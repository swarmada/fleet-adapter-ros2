# R3 — Isaac Sim, on rented hardware

**Do not start R3 until R1 and R2 are green.** Every hour on a GPU box spent debugging
the adapter is an hour you could have spent for free on your laptop. R1 and R2 exist to
make sure that by the time you are paying, the only unknowns left are Isaac-side.

**The claim R3 rests on:** the adapter is **unchanged**. `r1_smoke.py` and `r2_smoke.py`
run byte-identical against Isaac. If they need edits, Isaac is not configured as a
standard ROS 2 robot and the fix is on the Isaac side.

---

## 1. Hardware

Isaac Sim requires an **RT-core GPU** on **Linux x86_64**, with **>=16 GB VRAM** (24 GB+
preferred).

| Usable | Not usable |
|---|---|
| RTX 3090 / 4090 / 5090 · A10 / A10G · L4 · L40 / L40S · RTX A5000 / A6000 · RTX PRO 6000 | **A100 · H100 · H200 · V100 · T4** |

The right-hand column is the trap: those are the most common parts on GPU clouds and they
have **no ray-tracing cores**, so Isaac Sim will not render on them regardless of VRAM.
Filter listings on the GPU model, not the price. `cloud_bootstrap.sh` enforces this before
installing anything or pulling the ~30 GB image.

Isaac Sim runs on any provider offering one of the usable parts. Selecting one is a
deployment decision outside this repository.

## 2. Bootstrap the box

```bash
# on the rented instance, as root
curl -fsSL -o bootstrap.sh <your copy of testbed/cloud_bootstrap.sh>
bash bootstrap.sh
```

`cloud_bootstrap.sh` verifies the GPU has RT cores **before** installing anything,
then installs Docker, the NVIDIA Container Toolkit, and pulls the Isaac Sim image.
It refuses to continue on an A100/H100, which is the whole point.

You will need an **NGC API key** (free, `ngc.nvidia.com`) to pull
`nvcr.io/nvidia/isaac-sim:6.0.0`.

## 3. What changes from R2 — and what does not

| | R2 | R3 |
|---|---|---|
| Robot | `fake_robot_node.py --passive` | Isaac Sim robot prim |
| Odom / scan / TF | `r2_sensors.py` | `isaacsim.ros2.bridge` Action Graph |
| Nav2 | same stack | **same stack, `use_sim_time: true`** |
| Adapter | unchanged | **unchanged** |
| `r2_smoke.py` | passes | **must pass unedited** |

So R3 deletes two of your own nodes and adds an Isaac graph. Everything above the ROS 2
bus is carried over intact — which is why R2's Nav2 tuning is an investment, not
throwaway work.

### 3.1 Simulation time — the number one failure

Isaac publishes `/clock`. **Everything** downstream must run with `use_sim_time: true`:
Nav2, and any node of yours. Get it wrong and TF lookups fail with extrapolation errors,
Nav2 refuses goals, and none of the symptoms point at the cause.

```bash
make r3-params      # writes nav2_params.r3.yaml with use_sim_time flipped to true
```

The Action Graph must include a **`ROS2PublishClock`** node or there is no `/clock` to
use, and everything blocks forever waiting for time to start.

### 3.2 You author a graph, not a node

There is no `rclpy` node to write on the Isaac side. You build an **OmniGraph Action
Graph** in the USD stage and wire it to the robot's articulation:

| OmniGraph node | Produces |
|---|---|
| `ROS2PublishClock` | `/clock` — **required** |
| `ROS2PublishOdometry` | `/odom` |
| `ROS2PublishTransformTree` | `map → odom → base_link → laser` |
| `ROS2PublishLaserScan` | `/scan` (RTX Lidar) |
| `ROS2SubscribeTwist` → `DifferentialController` | consumes `/cmd_vel` |

`isaac_ros2_graph.py` in this directory authors that graph for one robot prim.
**It is unvalidated** — no Isaac runtime exists in the session that wrote it — so treat
the first run as the debugging step and expect NVIDIA's own tutorial to be the reference.

### 3.3 DDS across containers

Isaac ships its **own** bundled ROS 2 libraries and RMW. If Nav2's container uses a
different distro or RMW, discovery fails silently — topics list, no messages arrive.
Pin one distro (Jazzy) and one `RMW_IMPLEMENTATION` everywhere, use one
`ROS_DOMAIN_ID`, and prefer `--network=host` on the Linux box (which, unlike your Mac,
actually has one).

### 3.4 Real-time factor is not 1.0

Isaac steps physics at fixed dt but wall-clock rate follows GPU load. Under several
robots with RTX Lidar the sim may run slower than real time — message rates drop and
Nav2's controller-frequency assumptions strain. With `use_sim_time: true` this is
mostly handled; the residue shows up as a **cancel → confirmed-rest latency** that
differs from R2's. Record both. The R2 number is the honest one to quote for the e-stop
path, since it is not distorted by simulator pacing.

## 4. Run it

```bash
# 1. Isaac, headless, with the ROS 2 bridge and the graph
docker run --rm --gpus all --network=host \
  -e "ACCEPT_EULA=Y" -e "PRIVACY_CONSENT=Y" \
  -e ROS_DOMAIN_ID=42 \
  -v "$PWD/testbed:/testbed:ro" \
  nvcr.io/nvidia/isaac-sim:6.0.0 \
  ./python.sh /testbed/isaac_ros2_graph.py --robot-count 1

# 2. Nav2 with sim time
make r3-params
docker compose --profile r3 up nav2-r3

# 3. The SAME assertions, unedited
docker compose --profile r3 up r2-smoke
```

A green `r2_smoke.py` against Isaac is the R3 result. It says the adapter cannot tell
Isaac from Nav2-over-a-fake-robot — which is the property the whole vendor-neutral
adapter design claims and has never demonstrated.

## 5. Multi-robot — the mechanics

Only after single-robot R3 is green. **For the demo itself — including how to run it
with no robots at all, and what minimum hardware makes it real — see §6.**

**Isaac side:** replicate the Action Graph per robot with a namespace, so topics land at
`/robot1/odom`, `/robot2/odom`. `isaac_ros2_graph.py --robot-count N` is written for this.

**Adapter side:** one process per robot, each in its own namespace. This needs the
one-line change noted in `README.md` §5 — `adapter.py` uses `ap.parse_args()`, which
rejects a trailing `--ros-args`, and `start()` calls `rclpy.init()` with no arguments and
builds `Node(...)` with no `namespace=`.

**Nav2 side:** one namespaced Nav2 stack per robot. This is where GPU cost becomes real —
each Nav2 instance runs its own planner and costmaps, and that is CPU, not GPU. Size the
instance on **vCPU count**, not just the GPU model.

### The VDA5050 robot

`vda5050_shim.py` in this directory is that piece, and it is **the only genuinely new
code in the whole plan** — `fleet-adapter-vda5050` (3,488 lines, C1–C8 conformant, MQTT
client included) is already written and has simply never spoken to anything.

The shim does **not** touch Isaac's Python API. It sits outside Isaac and consumes the
same ROS 2 bridge output every robot already publishes, so **a VDA5050 robot in the
scene is authored exactly like a ROS 2 robot** — same Action Graph, same namespace.
`isaac_ros2_graph.py --robot-count 3` needs no VDA5050 awareness at all; only what
listens on the far end of `/robot2/odom` differs.

```
Isaac robot prim
  └── ROS2 Action Graph          (identical for every robot)
        ├── /robotN/odom, /robotN/cmd_vel
        ├──► robots 0,1   fleet-adapter-ros2 + Nav2      (ROS 2 path)
        └──► robot 2      vda5050_shim ──MQTT──► fleet-adapter-vda5050
```

Run it:

```bash
make r3-vda5050          # mosquitto + shim + the real adapter
make r3-vda5050-watch    # tail the raw MQTT: mosquitto_sub -t 'uagv/v2/#' -v
```

Topics follow `uagv/v2/{manufacturer}/{serial}/{connection,state,order,instantActions}`,
version string `2.0.0` — matched field-by-field against
`fleet_adapter_vda5050/profiles/vda5050.py`. Two details the adapter is strict about and
the shim gets right: `batteryCharge` is **already a percentage**, not 0–1; and an
`errors[]` entry with `errorLevel: FATAL` maps to `Failed` (and forces `phase=Error`)
while `WARNING` maps to `Degraded`. `--inject-error camera_front --inject-error-level FATAL`
drives that path on demand.

The MQTT **last will** is registered before connecting, publishing
`connectionState: CONNECTIONBROKEN`. The adapter fails safe on it — an unparseable or
missing `connectionState` is treated as broken, never as ONLINE — so killing the shim
container is a legitimate comms-loss test, not just a crash.

## 6. The multi-vendor demo

The demo this rung builds toward is **one control plane, one warehouse, robots on different
protocols driven by different adapters** — and it does not require Isaac, a GPU, or robots to
begin. Three simulated robots on a laptop, driven by `fleet-adapter-ros2` and
`fleet-adapter-vda5050` (via `vda5050_shim.py`), demonstrate the same property; Isaac replaces
what publishes `/odom` and nothing above it.

Build the demo without Isaac first. If it does not hold together there, rendering will not
save it — and if it does, this rung is a re-skin rather than a rebuild.

---

## 7. What R3 does not prove

Not physical hardware. Not contact dynamics or wheel slip. Not sensor noise
characteristics of any real lidar. A green R3 justifies retiring "simulated binding
only" for the ROS 2 path — **it does not justify moving any `end-to-end` grade to
`implemented`**, because no part of the vertical has touched a physical robot.

`drawbacks.md` says this today. Keep it saying it.
